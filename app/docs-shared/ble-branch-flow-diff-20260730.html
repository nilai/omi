链路 3 / 8

设备停录 → 状态广播的时机

这条是 memo→normal 那个现场故障的直接成因，而且是移植时新引入的：旧分支收到停录帧当场就广播，转码下载交给上层异步做；新分支把广播挪到了整条 finalize 链的末端。

这条最值得先修。把广播提到 finalize 之前，就回到旧分支的行为 —— 不需要动设备侧，也不需要加间隔。

旧分支胜 · 移植时新引入的回归

链路 4 / 8

录音控制权：双向 vs 单向

旧分支 App 可以主动开停录，和设备按键两条入口汇合到同一套状态应用逻辑；新分支只剩设备按键一条入口。

影响有限 · 录音本就该由按键驱动

链路 5 / 8

补传响应的分流

同一条 303 上会回来四种东西。旧分支四种都认，新分支认两种、丢两种 —— 丢的正好是两种失败。

旧分支胜 · 静默吞错

链路 6 / 8

memo / normal 这个字节的去向

协议上两种录音只差 303 起始帧偏移 3 的一个字节。旧分支把它变成枚举并落盘成 fileName → mode 索引；新分支只在内存里存了个 int?。

旧分支胜 · 语义被降级成裸字节

链路 7 / 8

断连续传的持久化　← 新分支更强

这条是移植时做加法的地方。旧分支只在断连事件里存一次，进程被强杀就全丢；新分支做了周期 checkpoint、sidecar 和残帧裁剪。

新分支胜 · 别在补回旧逻辑时覆盖掉这套

链路 8 / 8

掉线后怎么回来　← 新分支更强

另一处做加法的地方。旧分支靠 App 自己轮询，而且有两套机制并存；新分支把重连交给系统蓝牙栈。

新分支胜 · 这是移植时的真实改进

链路v1.0_bledev_2.0结论

合起来看是一件事：移植时把「连接生命周期管理」这一层整体重写了 —— 重连和续传这两块重写得更好，但握手初始化、状态查询、事件时序这三块在重写中丢了原有语义。

所以补回的时候要注意方向：链路 1/2/3/5/6 按旧分支补，链路 7/8 保持新分支不动。尤其别在把 e2c1a310 塞回 _probeAndJoinActiveDeviceRecordingOnConnect 时，顺手把周期 checkpoint 那套换回旧的一次性快照。

CK-1

补 0xE5 RTC 时间同步

P0 · 链路 1
改哪里
  • mp_note_ble_protocol.dart → MPNoteBleCommands 加 static const int syncRtc = 0xE5;
  • mp_note_ble_gatt_client.dart → 新增 syncRtc()，照 setRecordingTransportMode()（:165-181）的写法
  • mp_ble_recording_watcher.dart:457-465 → 在 setRecordingTransportMode 之前插一条
报文
  • E5 + 4 字节大端 Unix 秒：DateTime.now().millisecondsSinceEpoch ~/ 1000，UTC 不带时区偏移
参考旧实现
  • note_connection.dart:579-599（发送）
  • note_connection.dart:466-495（在 _initialize() 里的位置与顺序）
决策点
  • 旧实现有 _isInitialized 守卫，只在首连发一次。建议改成每次连接都发 —— 成本 5 字节，换来重连后设备时间也是对的
验收
  • 固件侧抓到 E5 xx xx xx xx
  • 把手机时间改掉 10 分钟 → 重连 → 设备 RTC 应跟随
  • 之后新录的文件名时间戳与手机时间一致
