3. 跟着一起丢的协议能力（这部分不是调试便利）

① e2c1a310 录音状态查询特征，整条没了。

旧 NoteUUIDs 有七个特征，第七个是只读的 recordStatus，格式 [Status 1B][FileNameLen 1B][FileName 变长]。新 MPNoteBleUUIDs 只剩 301–306 六个，这一条连常量都没保留。

旧：note_commands.dart:34-36 · note_connection.dart:1041-1070 · 新：mp_note_ble_protocol.dart:8-31

② 靠它撑起来的重连状态机，也一起没了。

旧代码重连后先 queryRecordStatus() 读一次特征，拿到确定的状态和文件名，再分三种场景走（note_connection.dart:360-395）：

  • A 设备还在录同一个文件 → 恢复 lastSeq，追加写，补传间隙
  • B 设备在录新文件 → 旧文件排进待下载队列，新文件正常收
  • C 设备空闲 → 旧文件排进待下载队列

新代码没有这条特征可读，改成了猜：发完 0D 10 之后干等 900ms，再看有没有 303 重放或 301 来流；还没有就再等 500ms（mp_ble_recording_watcher.dart:471-476）。等不到就判定"没在录音"。

这是个时间窗赌博：设备正好处在两帧之间的静默、或者链路刚恢复还没开始推流，就会被判成空闲——然后 App 立刻发起整轮批量导入，正踩在录音进行中。前一份文档里 memo→normal 那个问题的放大器，就是这条。

③ 命令常量从 20 条砍到 8 条。

丢的是：09 重启 · 0B 绑定/解绑 · 21/22 补传错误码 · E3 版本 · E4 U盘 · E5 RTC · E6 进 OTA · E8 存储 · E9 恢复出厂 · F3 WiFi · F6 OTA 控制。

21/22 有点意思：新代码在 _handleIncomingPacket 里用裸数字 0x21/0x22 过滤掉了这两个包（mp_note_ble_gatt_client.dart:413-415），但没保留常量、也没有任何错误处理——补传失败（文件不存在 / Seq 区间非法）被静默吞掉，上层不会知道。

4. 顺带解决了上一轮的悬念：Sync RTC 的确切格式

上一份文档里我说要你确认时间戳的字节序和基准 —— 不用问了，旧实现里写着：

[0xE5][ts>>24][ts>>16][ts>>8][ts] — Unix 秒，4 字节 大端，取 DateTime.now().millisecondsSinceEpoch ~/ 1000，也就是 UTC、不带时区偏移。note_ble_debug_provider.dart:531-545

跟 0x20 补传的 Seq 一样是大端，协议内部自洽。要在新 App 补这条命令，照抄这个格式即可，无需再跟固件对齐。

6. 怎么看这次移植

旧调试包的定位

  • 独立 APK，免登录，屏蔽全部业务
  • 扫描不过滤，任何 BLE 设备都能连
  • 协议全表铺开成按钮，逐条可点
  • 收发全量 hex 落抽屉，可回溯
  • 交付对象是方案商，用来验固件

新 App 里的这一页

  • 嵌在业务 App 里，kDebugMode 才出现
  • 依赖已建立的后台连接，不自己扫
  • 只有文件列表 / 删除 / 全删
  • 无任何通信日志
  • 交付对象是 App 开发自己，用来清设备文件

两者定位本来就不同，所以"整页照搬"不是目标。真正的问题在于：移植时把「调试 UI」和「协议能力」一起砍了。e2c1a310 和 0xE5 不是调试按钮，是业务链路要用的东西，它们是被捎带删掉的 —— 因为唯一引用它们的地方碰巧只有那个调试页和它背后的 provider。

如果只做一件事：把 e2c1a310 的读取补回业务侧的 MPBleTransport，让 _probeAndJoinActiveDeviceRecordingOnConnect 用一次确定性的读代替那 1.4 秒的观察窗。这一条同时修掉重连误判和 memo→normal 竞态的放大面，改动范围也最小。
