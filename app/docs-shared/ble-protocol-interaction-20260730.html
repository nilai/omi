0. 通道与角色

Service e2c1a300-7f4b-5e9d-bc23-1a2f3e4d5c6b，六个特征。连接成功后 App 一次性订阅其中四个 notify（mp_ble_transport.dart:338-426），MTU 请求 517（:320），命令一律 Write Without Response（:584-595）。

e2c1a301 · audioData设备→App。实时 Opus 流。[Seq 4B] 或 [Seq 4B][Flag 1B] + 分片，App 侧重组成 480B 帧

e2c1a303 · response设备→App。命令应答 + 主动上报（开始/停止录音）+ 0x20 补传载荷
e2c1a304 · otaFileApp→设备。代码中未使用
e2c1a305 · recordFile设备→App。文件导出流，[Seq 4B][Opus 480B]=484B/块；.txt 走透传
e2c1a306 · logFile设备→App。已订阅但无消费者

3. memo 短录音

协议上 memo 和 normal 只差 303 起始帧偏移 3 的一个字节：0x00=normal，0x01=memo（mp_note_ble_protocol.dart:93-100）。

而 App 当前对这个字节除了存起来什么都没做。sessionModeByte 被记录、被持久化进断点续传记录、被塞进状态事件——但全仓没有任何一处 if (mode == memo) 分支。memo 和 normal 走的是完全同一条处理链：同样边录边传、同样落盘、同样转 MP3、同样上传。

唯一一处按 memo/normal 分流的代码是 MPBleFileUtil.startLiveOpusRecording()（memo→0D 01 仅录音，normal→0D 10 边录边传，mp_ble_file_util.dart:1258-1310）——但这个 API 没有任何调用方，是死代码。实际生效的永远是连接时那条无条件的 0D 10。

4. 问题现场：memo 停止 → normal 开始 背靠背

这是你观察到「后一条像被忽略了」的那一幕。App 其实两条都收到、都解析了，问题出在停录处理是个耗时数秒的异步链，而它在最后一步才广播「已停止」——这条迟到的广播把中间那条「已开始」覆盖掉了。

设备
App 内部状态
t=0ms   303 ← 02 00 01（memo 停止）
进入 _handleDeviceRecordingStoppedOk，置 _finalizeAfterStopInProgress=true，随后 await 一串耗时操作 mp_ble_recording_watcher.dart:703-754
t≈20ms   303 ← 01 01 01 00（normal 开始）

次生问题（同一处）

  • _activeFileNameForRetransmit = null 和 _rtBuffer.reset() 在 finalize 中被无条件清空（:727-728）。若它们晚于新会话的赋值执行，新 normal 会话的 0x20 补传就永远发不出去（名字为 null 直接 return，:313-318）。
  • sameSessionAsResume 的判据是 _lastEmitted.activeFileName == fn（:680-681），而 _lastEmitted 就在几行之上刚被赋成 fn——这个条件恒为真，实际退化成「只要 _savedAudioPath 非空就当续传」。时序稍变就会把 normal 的音频 append 进 memo 的旧文件。
  • _finalizeAfterStopInProgress 是个全局互斥（:704-708）：finalize 期间到达的任何停录帧都被直接丢弃。memo 极短、normal 紧跟着又极快停止时，第二次停录会真的丢。

你的五个问题

① 设备没收到 App 的时间校准指令

确认：App 根本没有这个功能。全仓搜 0xE5 / RTC / 时间同步，命中 0 处代码。命令常量表（mp_note_ble_protocol.dart:69-85）里只有 0x01 0x02 0x03 0x04 0x05 0x0D 0x20 0xE1 八条，没有 0xE5。

但这条命令不只是调试功能。上一版 App（v1.0_ble 分支）把它放在连接初始化 _initialize() 的第一步，每次首连必发，顺序是 RTC 同步 → 检查绑定状态 → 读录音状态（note_connection.dart:466-495 / 579-599）。这一版重写连接流程时，整个初始化序列都没有搬过来，只剩下 0D 10。

所以不是发丢了、不是时序问题，是这一版没写。报文格式不需要你们再确认 —— 上一版代码里就是现成的：

E5 + 4 字节 大端 Unix 秒　（DateTime.now().millisecondsSinceEpoch ~/ 1000，UTC 不带时区偏移）

我们照这个补回去，插在 0D 10 之前。只有一点想跟你们对一下：上一版发的是 UTC 秒，而设备生成的文件名形如 20260730_101530 —— 这个时间是本地时间还是 UTC？如果是本地时间，设备侧的时区是从哪来的？这决定我们是发 UTC 秒、还是发本地化之后的秒数。

② 连接后设备没收到 e5 开头的数据包

同上，就是同一件事——0xE5 就是 Sync RTC。连接后 App 发出的唯一一条主动命令是 0D 10（切边录边传，mp_ble_recording_watcher.dart:458-465）。之后才可能有 0x03 / 0x04 / 0x05 / 0xE1。设备侧抓不到 E5 是预期行为，不用继续查固件。

③ 停 memo 和开 normal 几乎同时发过去，App 是不是把后一条忽略了？

没有忽略——两条都收到、都解析了。303 的监听是同步回调，停录处理用的是 unawaited(...) 异步跑，不会阻塞后一条帧的解析。

真正的问题是停录处理链太长，而且把「已停止」的对外广播放在了链条最末端。它要做：关文件 → Opus 转 MP3（CPU 密集，秒级）→ 发 0x03 找配对 txt → 发 0x04 导出 txt → 写本地记录 → 发 0x05 删设备上的 opus 和 txt。全跑完才广播「已停录」（mp_ble_recording_watcher.dart:725-743）。这条广播晚了几秒钟落地，把中间那条「normal 已开始」的状态盖掉了，App 于是认为设备不在录音，顺手又发起一整轮批量导入——正好压在 normal 录音进行中。

所以：这个不用你在设备侧加间隔。间隔多久都没用——App 这条链本身就要几秒，你没法靠延时绕开。而且从产品上讲 memo 结束立刻转 normal 是合理操作，不该要求固件迁就。修在 App 侧，三处：

  1. 停录 finalize 先广播「已停止」，再去做转码/拉 txt/删文件——状态广播不该等 I/O。
  2. finalize 前把 opusPath/fileName 快照进局部变量，全程不再碰 _savedAudioPath、_activeFileNameForRetransmit、_rtBuffer 这些属于「当前会话」的字段。
  3. 广播前比对会话身份：若此刻已有新会话在跑（新文件名 ≠ 本次 finalize 的文件名），就不发这条「已停止」。

顺带修掉 sameSessionAsResume 那个恒真判据（:680-681），否则时序一变就会把 normal 的音频写进 memo 的文件里。

如果设备侧愿意配合、成本很低的话，有一条能显著降低风险：在停止帧和开始帧之间留 ≥200ms。这不能修好上面的根因，但能避开「finalize 刚起步、字段还没快照」这段最脆弱的窗口。要不要做由你定，App 侧的修复我这边照做不误。

④ App 是实时传输，还是录完再传文件？

两段要分开看，答案不一样。

设备 → 手机：实时。连接后 App 无条件发 0D 10（边录边传），设备录音时通过 e2c1a301 逐帧推 Opus，App 一帧一帧直接落盘，丢帧就发 0x20 补传。录到哪传到哪，不等结束。

手机 → 服务器：录完再传。录音期间不上传任何东西。02 00 01 到达后才 Opus→MP3、拉 txt、写本地记录，然后跑完批量导入，最后才把这一批（实时那条 + 批量导入的）合并去重、统一上传（mp_home_cubit.dart:794-814）。

还有一条兜底：即使实时流那一路出了问题（App 没连上、sink 没开成、中途断连），停录后的批量导入会通过 0x03 → 0x04 → 0x05 把设备上的完整文件重新拉一遍。所以实时流是「省时间」，不是「唯一的数据来源」。

⑤ 「这个应该在设备这里，因为无论 App 是否接收到、当前是否在录音都不影响设备」

关于设备自主性，你说得对，代码完全支持这个判断。App 从不发送 0x01/0x02——全仓没有任何一处调用（MPNoteBleCommands.startRecording/stopRecording 两个常量只被用来解析收到的帧）。录音的起停 100% 由设备按键决定，App 是纯观察者。设备离线照录不误，文件留在设备上，下次连上批量导入。

但有一点要说清楚：设备不受影响 ≠ 这件事该由设备解决。③ 里那个问题的失败面完全在 App 的状态机内部（迟到的广播覆盖了新状态），设备无论怎么发都不会让 App 自愈。所以责任划分是：设备继续按现在的方式发，不用改；修复在 App 侧。唯一可选的设备侧配合就是那个 ≥200ms 间隔，属于降风险，不是必需。

反过来有一条确实依赖设备：在这一版里，303 的主动上报（01 … / 02 …）是 App 感知录音状态的唯一来源 —— 上一版还会读 e2c1a310 录音状态特征做交叉确认，这一版没搬过来（见下节第 1 条）。所以目前设备必须保证这两条帧一定发出、且带完整的 mode 和文件名字段，否则 App 会漏状态。

需要固件侧确认或配合的三件事

除下面三条之外，本次分析涉及的问题都在 App 侧，设备不需要改动。

1 · e2c1a310 录音状态特征，当前固件还在吗？

我们准备把「读这条特征」补回连接流程，用它替代现在那个 900 ms 观察窗（问题③ 里提到的误判风险，根子在这）。上一版 App 是这么用的：

只读特征 e2c1a310-7f4b-5e9d-bc23-1a2f3e4d5c6b，返回 [Status 1B][FileNameLen 1B][FileName 变长]

要确认两点：① 当前固件版本是否仍实现这条特征；② 返回格式是否仍是上面这个。如果固件已经改了或去掉了，请给新的读法 —— 这条是我们修重连误判最直接的依据，没有它只能继续靠时间窗猜。

2 · 0xE5 的时间基准：UTC 还是本地时间？

报文格式我们已经从上一版代码里确认了（E5 + 4 字节大端 Unix 秒），不需要你们再出方案。唯一想对齐的是基准：

上一版发的是 UTC 秒。而设备生成的文件名形如 20260730_101530 —— 这个时间是本地时间还是 UTC？如果是本地时间，设备侧的时区是从哪来的（固件固定 UTC+8？还是另有下发通道）？这决定我们补回去时是发 UTC 秒、还是发本地化之后的秒数。答错了文件名时间会整体偏 8 小时。

3 · 停止帧与开始帧之间能否留 ≥ 200 ms？可选

这条不是必须的，问题③ 的根因在 App 状态机，我们会自己修。

但如果固件侧加这个间隔成本很低，可以顺手做：它能避开 App 停录处理刚起步、还没把会话字段快照下来的那一小段脆弱窗口，属于降风险。我们不依赖它，你们评估后告诉我们做不做即可。
